# 数据契约 v0.1

## 三层与事实粒度

- `reported`：来源明确显示的值。截图、看板不是平台真实性证明。
- `derived`：基于已定位值进行可重算的算术。不能继承来源中的因果结论。
- `hypothesis`：解释或动作候选。必须附成立所需的证据。

事实记录包含 `id`、JSON Pointer `pointer`、`raw`、`kind`。输入文件 SHA-256 在 manifest 中保存；原始文件必须可重新访问。叙述、标注和数值字段分开使用。原始输入只读，不在公开仓库保存。

## WorkBuddy 适配

安全读取 `const DATA = { ... }`、可选 `const NEW = { ... }`；解析器不 eval JavaScript。`NEW` 是附加观察，不能覆盖 DATA 的周期和数值。只支持 JSON 常量；函数、单引号对象、动态网络数据不自动解释。

DATA 为 shop-key 到对象的映射。支持字段 `name/period/updated/kpis/trade/products/live/refund/diagnosis`；缺失字段保留缺口。NEW 的 b1/b2 需由 NEWKEY 显式关联，关联缺失时不猜店铺顺序。不同部分可能分别是近7天、近30天和单场快照。

逐场表头写“成交金额”，直播汇总写“支付金额”时不能直接裁定两者应相等；金额差额只作口径核对线索。订单汇总也需核对归属窗口、延迟成交、状态、视角和采集时间。同一分钟不是同场证明；稳定场次ID缺失时不得自动融合外部明细。

同场“观看人数”与“观看次数”不应被强制对平。把各场去重人数相加也不是周去重人数。

## Canonical JSON

用于经过人工或 Agent 明确字段映射的来源包：

```json
{
  "schema_version": "1",
  "shops": {
    "synthetic-shop": {
      "name": "合成示例店",
      "period": "明确的周期",
      "live": {"sessions": []}
    }
  },
  "observations": {},
  "bindings": {},
  "provenance": [
    {"source_file": "原文件位置", "sha256": "实际哈希", "locator": "工作表/单元格或行", "mapping_note": "具体映射规则"}
  ]
}
```

shops 内适配的字段与 WorkBuddy DATA 相同。canonical provenance 是映射者提供的记录；verify_run 复核 canonical 输入本身，**不会证明外部原表的单元格**。需要单独回读原文件后才能宣布映射准确。

## 计算边界

- 空、`-`、未知不补0。零分母的比率为空。不解析“万+”、金额区间为精确数。
- 百分比变化与百分点变化不同。百分比字段除以100后参与计算。
- 商品支付减同快照退款只称“扣退款后金额（快照）”，不称净利润；观察期和对应批次不明时只作为核查线索。
- 店铺消耗除以全量直播曝光不是付费曝光效率；不能用总观看减自然观看直接当千川原生归因。
- D7/D14/D30是观察年龄，不能把“上一周订单”整体视为相同年龄或最终成熟。结算亦可能对应历史订单。
- 画像占比/TGI不是人群转化率。零成交先核对缺数、挂车、账号与归因延迟。
